SteerBench

An agent that carries out the next step on its own is useful right up until it acts without permission, before a result has come back, or on a fact that stopped being true an hour ago. Most agent benchmarks score whether the task got done. SteerBench scores the decision made at each step about whether to keep going.

Every trace is one decision point: a task, a scoped memory, and the latest observation. The model picks one of five interventions. The benchmark has 2,500 traces across six domains (coding, database, finance, calendar, research and science QA), split 2,000 for training and 500 held out. Each trace carries a gold label and a one-line rationale.

Measuring the baseline

The first measurement is a small open model with no fine-tuning: TinyLlama-1.1B, zero-shot, on 100 traces. It was shown the task, memory and observation, and asked for a JSON object naming one intervention and a reason.

What the number hides

Two thirds of the answers contain no readable decision. That makes 11% hard to interpret: it can't distinguish a model that lacks the judgment from one that has it and can't write it down.

When this model does commit to a decision, it mostly decides to keep going.

Of the 33 answers that named an intervention, 26 chose ACT. That lean toward acting is the behaviour SteerBench exists to measure, and it shows up even through the noise of a model that mostly can't follow the format.

The first attempt to fine-tune on the training traces ran rank-16 LoRA (4.51M trainable parameters) on a laptop CPU. After 13 optimizer steps the estimate to finish was 4 to 10 hours.3 That's too slow to compare several training methods, each with more than one seed, so no fine-tuned result exists yet.

Separating format from judgment

The next experiment runs on lab GPUs. The main model is Qwen2.5-1.5B-Instruct, and the first step re-runs TinyLlama on the full 500-trace test set with the new parsers, so the old baseline gets a proper sample size. The same harness also packages SteerBench as an environment for Tinker's open-source cookbook, so every arm can move to managed training without changing the benchmark. The runs below have not happened yet; this section describes what they will measure and why.

Pricing mistakes

For reinforcement learning, a wrong answer has to cost something, and not every wrong answer should cost the same. Acting when the agent should have asked is worse than asking when it could have acted. Two reward schemes are compared from the same starting checkpoint.

The comparison

Six arms, all scored on the same 500 held-out traces. Differences between arms are reported with a paired bootstrap over trace ids, so a gap of a few points can be told apart from noise.

  1. On local GPUs each letter is scored as the log-likelihood of that answer continuing the prompt, and training uses the same scores, so what is trained is what is measured. How it's built

The harness is a small Python package with two backends that share one prompt, one pair of parsers, one reward and one metrics module. On lab GPUs it uses Hugging Face models with LoRA and training loops written out by hand. On Tinker, SteerBench is a subclass of the cookbook's single-turn environment. Either way, every outcome is logged as its own training metric, so a run's curves show which mistakes are going away, not only whether reward went up.

The RL loop is short enough to state in full. For each training trace, sample eight answers and score each with the reward scheme. An answer's advantage is its reward minus the mean reward of its group of eight. Take one gradient step on the negative sum of advantage times the answer's log-probability, divided by the number of answer tokens. A group where all eight answers scored the same carries no signal and is skipped, and the log records how often that happens.

  • One prompt builder shared by every arm, so arms differ only in readout and training.
  • Each result keeps the raw text of every answer next to both parses, plus the model, checkpoint path, prompt hash and test-file hash. Any number traces back to its run and can be re-scored without sampling again.
  • A deterministic train/test split that doesn't depend on file order, and a data card that warns if any label is missing from test.
  • 54 tests that run on a laptop CPU: parsers, reward properties, metrics and split, the Tinker environment driven through the cookbook's own interfaces, and every local training arm run end to end on a tiny random model.

What broke

Each of these was caught by a test before any compute was spent.

  1. The reward ablation couldn't be launched from the command line

    The RL config received a finished dataset-builder object, and the config library then refused overrides of its fields. The documented command for the symmetric-reward run would have failed at startup.

    The builder is now passed as a factory with its fields as sub-parameters. A test builds both reward schemes from one blueprint.

  2. The split could drop whole labels from the test set

    Splitting each (label, domain) group separately and rounding sent every one-trace group to training. On a small file, the test set lost all ACT and REMEMBER examples.

    The split now samples systematically over traces ordered by label, domain, then id hash, so test size is exact and every label gets its share.

  3. A one-line trace file reported errors in the wrong place

    A JSONL file holding a single record also parses as one JSON document, so a bad label was reported as item 0 instead of line 1.

    .jsonl files are now always read line by line.

  4. The training library couldn't run its own tests without a GPU

    The first local backend used TRL 1.15. Its trainers always swap in a fused Triton kernel for the loss, and on a machine with no GPU that kernel raises before the first step, so the training code could not be checked anywhere except the cluster.

    SFT, RL and decision training are now short hand-written loops over a shared log-probability function. Every arm runs end to end on a tiny random model on CPU in seconds.

Limitations

The baseline is 100 traces from one small model, and its metrics come from an earlier script whose definitions are close to, but not the same as, the new harness. Re-scoring those raw outputs with the new parsers is the first thing the harness does. Each trace has exactly one gold label, though some situations could reasonably allow two. The reward values are a design choice, which is why the symmetric arm exists. Results on 1 to 1.5B models may not carry over to larger ones.
